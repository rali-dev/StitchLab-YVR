🎙️ Sprechtext

4 · Erster Begriff — die 3-Teile-Regel 1–2 Min

📝 Hier kommt zum ersten Mal deine Definition · Vorteile · Nachteile-Box. Konzept immer mit einer Alltags-Analogie einführen — hier: das Restaurant.

Zweitens, das Backend. Es arbeitet im Verborgenen auf einem Server. Prüft dein Passwort, entscheidet ob du Admin bist, holt die richtigen PLATZHALTER: Inhalte/Daten. Das ist die Küche — der Gast sieht sie nie, aber ohne sie gibt’s kein Essen.

Und drittens, die Datenbank. Der Ort, an dem dauerhaft alles gespeichert wird — alle Nutzer und PLATZHALTER: Inhalte/Daten. Das ist die Vorratskammer.“

📦 Begriff: Frontend / Backend / Datenbank
Definition
Die drei Schichten, aus denen fast jede Web-App besteht: Anzeige · Logik · Speicher.
Vorteil
Jeder Teil hat eine klare Aufgabe → leichter zu bauen, zu verstehen und zu reparieren.
Nachteil
Man muss drei Dinge lernen statt nur eins — am Anfang mehr Aufwand.
Alternative
Man könnte alles in eine Datei packen. Macht bei echten Projekten niemand, weil es sofort unübersichtlich wird — deshalb trennen auch wir sauber.
🎙️ Sprechtext

„Merk dir diese drei Wörter — Frontend, Backend, Datenbank. Den ganzen Kurs über wirst du genau wissen, an welchem der drei Teile wir gerade arbeiten.“

02 Kapitel · Teil 0

Wie denkt ein Senior-Team?

⏱ 6–8 Min ⌨ 0 Zeilen Code 🎯 Struktur & Denkweise verstehen

1 · Kurzer Rückblick & heute ~30 Sek

🎙️ Sprechtext

„Willkommen zurück! Im letzten Kapitel haben wir gesehen, was wir bauen — und die drei Teile jeder Website kennengelernt: Frontend, Backend, Datenbank. Heute schauen wir uns an, wie ein echtes Entwickler-Team an so ein Projekt herangeht. Denn Profis fangen nicht einfach an zu tippen — sie denken erst nach. Und genau diese Denkweise nehme ich dir heute ab.“

📝 Noch immer kein Code. Erst die Denkweise, dann die Werkzeuge (ab Kapitel 4). Super Simple Dev baut Verständnis vor Tastatur.

2 · Das Team & die Rollen ~2 Min

🎬 Bildschirm

Einfache Grafik: eine Küchen-Brigade / ein Team mit Rollen-Kärtchen.

🎙️ Sprechtext

„Bleiben wir bei unserem Restaurant. Ein gutes Restaurant wird nicht von einer Person allein geführt — es gibt Rollen. Genauso ist es in einem Software-Team. Schauen wir uns die wichtigsten an:

Der Architekt entscheidet, wie das Gebäude aufgeteilt wird — wo die Küche ist, wo die Vorratskammer. In Software heißt das: Welche Teile gibt es, und wie reden sie miteinander?

Der Backend-Entwickler ist der Koch — er sorgt dafür, dass im Verborgenen alles richtig zubereitet wird. Der Frontend-Entwickler ist der Kellner — er bringt das Ergebnis schön angerichtet zum Gast. Und alle folgen demselben Rezeptbuch, damit nichts durcheinandergerät.“

📝 Die Rollen sind eine Denkhilfe, keine echten Personen — du übernimmst sie alle. Der Punkt: Für jede Aufgabe gibt es eine klare Verantwortung.

3 · Die goldene Regel: erst denken in Kästchen ~1,5 Min

🎙️ Sprechtext

„Die wichtigste Gewohnheit von Profis ist einfach: Jedes Ding hat genau eine Aufgabe. Man mischt nicht alles zusammen. Der Kellner kocht nicht, der Koch bedient nicht. In Software nennt man das „Trennung der Zuständigkeiten“. Klingt fancy, heißt aber nur: Kleine, ordentliche Kästchen statt einem riesigen Chaos-Klumpen.“

📦 Begriff: Trennung der Zuständigkeiten (Separation of Concerns)
Definition
Jeder Teil des Codes kümmert sich um eine Sache — nicht um mehrere gleichzeitig.
Vorteil
Wenn etwas kaputt ist, weißt du sofort wo du suchen musst. Änderungen bleiben lokal, statt alles umzuwerfen.
Nachteil
Mehr Dateien und Ordner — am Anfang fühlt es sich nach „viel“ an.
Alternative
Alles in eine Datei stopfen. Geht bei winzigen Projekten, wird aber ab Größe X zur Hölle — deshalb machen es Profis nie.

4 · Wie unser Projekt aufgeteilt ist ~2 Min

🎬 Bildschirm

VS Code öffnen, den Datei-Explorer links zeigen. Ordner apps/ und libs/ aufklappen.

🎙️ Sprechtext

„Und jetzt der clevere Teil. Unser ganzes Projekt — Frontend und Backend — wohnt in einem einzigen Ordner. Man nennt das ein Monorepo: ein Haus mit vielen Zimmern, statt vieler kleiner Häuser, zwischen denen man ständig hin und her rennen muss. Schauen wir rein.“

apps/ # die lauffähigen Programme frontend/ # die Website, die man im Browser sieht backend/ # der Server, der im Verborgenen arbeitet libs/ # die Bausteine, ordentlich sortiert frontend/ # Seiten: home, deine Seiten backend/ # Bereiche: identity, deine Domänen shared/ # das gemeinsame Rezeptbuch (contracts)
🎙️ Sprechtext

„Siehst du, wie ordentlich das ist? In apps liegen die zwei laufenden Programme — Website und Server. Und in libs liegen die einzelnen Bausteine, sauber nach Thema sortiert. Jeder Bereich hat sein eigenes Zimmer. Genau die Trennung, über die wir gerade gesprochen haben, nur zum Anfassen.“

📦 Begriff: Monorepo
Definition
Ein einziges Projekt-Verzeichnis, das mehrere Programme (Frontend, Backend) und alle Bausteine zusammen enthält.
Vorteil
Alles an einem Ort, ein gemeinsames Rezeptbuch, Änderungen über Frontend + Backend in einem Schritt.
Nachteil
Der eine Ordner wird groß; man braucht ein Werkzeug, das Ordnung hält (bei uns: NX — kommt in Kapitel 4).
Alternative
Getrennte Repos („Polyrepo“) — jedes Programm für sich. Nutzen große Firmen manchmal, ist aber für ein Solo-Projekt wie unseres mehr Verwaltungsaufwand. Deshalb: Monorepo.

5 · Das gemeinsame Rezeptbuch ~1 Min

🎬 Bildschirm

Auf libs/shared/contracts zeigen.

🎙️ Sprechtext

„Ein letzter Gedanke, den Profis lieben. Damit Kellner und Koch nicht aneinander vorbeireden, gibt es ein gemeinsames Rezeptbuch. Bei uns heißt es contracts — also „Verträge“. Darin steht ganz genau, wie ein PLATZHALTER: Kern-Objekt von StitchLab-YVR aussieht: welche Felder es hat, PLATZHALTER: ggf. in welchen Sprachen. Frontend und Backend halten sich beide daran. So kann sich niemand vertun — und wenn wir später etwas ändern, meckert der Computer sofort, falls es nicht mehr passt.“

📝 Verbesserung / Detail fürs Video: Alle Bausteine sprechen denselben Import-Namen @stitchlab-yvr/… (bewusst kleingeschrieben). Das contracts-Paket ist @stitchlab-yvr/shared-contracts — die einzige Brücke zwischen Frontend und Backend.

📝 Das ist der erste Aha-Moment für „warum diese Kombination“: geteilte Verträge sind der Grund, warum Fehler früh auffallen statt beim Nutzer.

6 · Abschluss & Ausblick ~30 Sek

🎙️ Sprechtext

„Fassen wir zusammen: Profis denken erst in Kästchen mit klaren Aufgaben, packen alles ordentlich in ein Monorepo und einigen sich über ein gemeinsames Rezeptbuch. Mehr Magie steckt gar nicht dahinter.

Im nächsten Kapitel gehen wir die vier großen Säulen unseres Projekts durch — Architektur, Security, Design und Datenbank — damit du das ganze Bild hast, bevor wir die erste Zeile Code schreiben. Bis gleich!“

🎥 Aufnahme-Checkliste für dieses Kapitel

  • VS Code offen, Datei-Explorer sichtbar, apps/ und libs/ vorbereitet zum Aufklappen
  • Optional: simple Grafik „Team-Rollen“ (Architekt · Koch · Kellner · Rezeptbuch)
  • Schrift im Editor groß genug (mind. 16–18px), damit Ordnernamen lesbar sind
  • Nichts anklicken/öffnen, was noch nicht erklärt wurde — nur die Ordner-Struktur zeigen
03 Kapitel · Teil 0

Die 4 Säulen deines Projekts

⏱ 8–10 Min ⌨ 0 Zeilen Code 🎯 Das ganze Bild + „warum diese Kombination?“

1 · Rückblick & heute ~30 Sek

🎙️ Sprechtext

„Willkommen zurück! Wir wissen jetzt was wir bauen und wie ein Team denkt. Heute das letzte Theorie-Kapitel — danach schreiben wir wirklich Code. Ich zeige dir die vier Säulen, auf denen unser Projekt steht. Wenn eine davon wackelt, wackelt die ganze Seite. Am Ende beantworte ich die wichtigste Frage: Warum ausgerechnet diese Kombination von Werkzeugen?“

🖥️ Stichpunkte einblenden
  • 🏛️ Architektur — die Ordnung
  • 🔐 Security — der Schutz
  • 🎨 UI & Design — das Erlebnis
  • 🗄️ Datenbank — das Gedächtnis

2 · Säule 1 — Architektur ~2 Min

🎬 Bildschirm

Ordner-Baum aus Kapitel 2 kurz zeigen, dann in libs/backend/deine-domäne hineinzoomen (Unterordner domain / application / infrastructure / adapters).

🎙️ Sprechtext

„Säule eins: die Architektur — also die Ordnung. Wir bauen keinen großen Klumpen, sondern getrennte Bereiche: PLATZHALTER: deine Domänen, z. B. identity, …. Jeder Bereich ist wie ein eigenes kleines Geschäft mit klaren Wänden drumherum. Fachleute nennen das Domain-Driven Design — man ordnet den Code nach echten Themen aus der Wirklichkeit, nicht nach Technik.

Und innerhalb jedes Bereichs gibt es Schichten: eine für die reinen Regeln, eine für die Abläufe, eine für die Technik-Anbindung. Das klingt viel — aber es sorgt dafür, dass wir später eine Sache ändern können, ohne dass zehn andere kaputtgehen.“

📦 Begriff: Modular Monolith & Domain-Driven Design (DDD)
Definition
Ein einziges Programm (Monolith), aber innen sauber in fachliche Bereiche mit klaren Grenzen aufgeteilt.
Vorteil
Ordnung wie bei den „großen“ verteilten Systemen, aber viel einfacher zu bauen und zu starten — perfekt für ein Team von einer Person.
Nachteil
Am Anfang mehr Ordner und etwas Disziplin nötig; die Vorteile zeigen sich erst, wenn das Projekt wächst.
Alternative
Microservices — viele winzige Einzel-Programme. Sehr mächtig, aber für uns massiv überzogen (viel mehr Aufwand, Kosten, Komplexität). Deshalb: Modular Monolith.

3 · Säule 2 — Security ~2 Min

🎬 Bildschirm

Als normaler Nutzer versuchen, die Adresse /admin direkt aufzurufen → wird abgewiesen/umgeleitet. Danach kurz die Login-Seite zeigen.

🎙️ Sprechtext

„Säule zwei: Security — der Schutz. Schau: Wenn ich als normaler Nutzer versuche, in den Admin-Bereich zu kommen, lässt die Seite mich gar nicht rein. Das ist kein Zufall, das ist ein Wächter, der an der Tür steht.

Drei Dinge machen wir richtig sicher. Erstens: Passwörter speichern wir niemals im Klartext — sie werden mit einem Verfahren namens bcrypt unkenntlich gemacht. Zweitens: Wer eingeloggt ist, bekommt einen digitalen Ausweis in einem sicheren Keks — einem Cookie —, der sich sogar regelmäßig selbst erneuert. Und drittens: PLATZHALTER: geschützte Dateien/Downloads, falls vorhanden gibt es nur über zeitlich begrenzte Links, die nach kurzer Zeit ablaufen. Wer verstanden hat, wer was darf, hat Security zur Hälfte verstanden.“

📦 Begriff: Authentifizierung & Autorisierung
Definition
Authentifizierung = wer bist du? (Login). Autorisierung = was darfst du? (Nutzer vs. Admin).
Vorteil
JWT-Cookie + Rollen sind Industrie-Standard: sicher, bewährt, funktioniert auf jedem Gerät.
Nachteil
Man muss es genau richtig machen — kleine Fehler sind hier gefährlich. Deshalb erklären wir es Schritt für Schritt.
Alternative
Fertige Login-Dienste (z. B. Auth0, Firebase Auth). Bequem, aber du lernst nichts über den Kern — und wir wollen es verstehen. Deshalb bauen wir es selbst.

4 · Säule 3 — UI & Design ~2 Min

🎬 Bildschirm

Live: Tag/Nacht umschalten, dann Sprache wechseln (falls RTL: Seite dreht auf rechts-links). Auf Handy-Größe verkleinern, um „responsive“ zu zeigen.

🎙️ Sprechtext

„Säule drei: UI und Design — das Erlebnis. Eine Seite kann noch so klug gebaut sein — wenn sie hässlich oder unbedienbar ist, kommt niemand wieder. Wir nutzen Angular, um die Oberfläche aus kleinen, wiederverwendbaren Bausteinen zusammenzusetzen, und Tailwind, um sie schnell und einheitlich zu gestalten.

Das Schöne: Farben und Abstände definieren wir einmal zentral — als „Design-Tokens“. Deshalb funktioniert der Dark-Mode mit einem einzigen Umschalter, und deshalb sieht alles zusammengehörig aus. Und weil unsere Seite mehrsprachig ist — PLATZHALTER: Sprachen, ggf. inkl. RTL von rechts nach links —, denken wir Design von Anfang an flexibel.“

📦 Begriff: Design-Tokens & Tailwind
Definition
Zentrale Werte für Farben, Abstände, Schriften. Alle Bausteine benutzen sie — niemand schreibt Farben doppelt.
Vorteil
Einheitliches Aussehen, Dark-Mode & Themes fast geschenkt, Änderungen an einer Stelle wirken überall.
Nachteil
Tailwind-Klassen im HTML sehen anfangs „voll“ aus — Gewöhnungssache.
Alternative
Klassisches CSS von Hand oder große Fertig-Bibliotheken (Bootstrap). Wir nehmen bewusst Tailwind v4 — weil es schneller und konsistenter ist.

5 · Säule 4 — Datenbank ~2 Min

🎬 Bildschirm

Optional: Supabase-Tabellenansicht ODER die Datei schema.prisma zeigen — die Tabellen deine Tabellen, z. B. User, ….

🎙️ Sprechtext

„Säule vier: die Datenbank — das Gedächtnis. Alles, was dauerhaft bleiben soll, landet hier: jeder Nutzer und PLATZHALTER: deine Kern-Daten von StitchLab-YVR. Wir nutzen PostgreSQL, eine sehr solide, kostenlose Datenbank, die in der Cloud bei Supabase läuft — wir müssen also keinen eigenen Server aufsetzen.

Und statt kryptische Datenbank-Befehle von Hand zu schreiben, reden wir über ein Werkzeug namens Prisma mit ihr — in normalem, lesbarem Code. Der Clou: Prisma kennt unsere Tabellen ganz genau, und diese Struktur passt exakt zum Rezeptbuch aus Kapitel 2. So spielt alles zusammen.“

📦 Begriff: Relationale Datenbank & Prisma (ORM)
Definition
Daten in Tabellen mit Beziehungen. Prisma ist der Übersetzer zwischen unserem Code und der Datenbank.
Vorteil
Verlässlich, weit verbreitet, und mit Prisma typsicher — der Computer warnt dich, bevor du einen Fehler machst.
Nachteil
Man muss die Struktur (das „Schema“) im Voraus planen — spontanes Chaos ist nicht erlaubt (was gut ist).
Alternative
Dokument-Datenbanken wie MongoDB. Flexibler, aber weniger streng — und für klar verknüpfte Daten wie unsere sind Tabellen die bessere Wahl. Deshalb: PostgreSQL.

6 · Warum genau diese Kombination? ~1,5 Min

🎙️ Sprechtext

„Jetzt die wichtigste Frage: Warum diese Werkzeuge und nicht tausend andere? Es gibt einen roten Faden, der alles verbindet.“

2 · Was ist NX wirklich? ~2 Min

🎙️ Sprechtext

„Erinnerst du dich an unser Bild aus Kapitel 2 — das Haus mit vielen Zimmern, das Monorepo? Ein großes Haus braucht einen guten Hausverwalter. Genau das ist NX. Ein Monorepo ist nur ein Ordner — NX ist das Werkzeug, das darin für Ordnung sorgt.

NX macht drei Dinge für uns. Erstens: Es erzeugt neue Bausteine per Befehl, immer in derselben sauberen Struktur — du musst nie bei Null anfangen. 📦 Begriff: NX (Monorepo-Werkzeug)
Definition
Ein „Verwalter“ für Monorepos: erzeugt Bausteine, kennt ihre Abhängigkeiten und baut/testet nur das, was sich geändert hat.
Vorteil
Einheitliche Struktur per Knopfdruck, klare Grenzen zwischen Bereichen, spürbar schnellere Builds & Tests.
Nachteil
Ein weiteres Werkzeug mit eigenen Befehlen, das man lernen muss — ein bisschen Einstiegshürde.
Alternative
Turborepo, Lerna oder pure npm-Workspaces. Alle können Monorepos — aber NX bringt für Angular und NestJS die beste Integration mit. Deshalb: NX.

3 · Warum NX und nicht getrennte Repos? ~1,5 Min

🎙️ Sprechtext

„Man könnte Frontend und Backend auch in zwei getrennte Ordner stecken — zwei getrennte Projekte. Das nennt man „Polyrepo“. Klingt erstmal einfacher, hat aber einen fiesen Haken: Sobald sich unser gemeinsames Rezeptbuch ändert, musst du an zwei Stellen nachziehen und hoffen, dass beide zusammenpassen. Genau da schleichen sich Fehler ein.“

🖥️ Stichpunkte einblenden — NX-Monorepo vs. getrennte Repos
  • Ein Ort für alles: Frontend, Backend, Verträge — du wechselst nie das Projekt.
  • Eine Änderung, ein Schritt: Rezeptbuch anpassen und beide Seiten in einem Rutsch mitziehen.
  • Der Computer passt auf: NX warnt, wenn ein Baustein etwas benutzt, das er nicht darf.
  • Weniger Verwaltung: eine Installation, ein Regelwerk — statt zweimal alles doppelt.

📝 Kurz halten — das Monorepo-Warum kam schon in Kap. 2. Hier nur der direkte Vergleich, warum wir es mit NX machen.

4 · Kurz erklärt: Was heißt „zoneless“? ~1 Min

🎙️ Sprechtext

Definition
Angular ohne das automatische „Änderungs-Radar“ Zone.js — Updates laufen gezielt über Signals.
Vorteil
Schneller (weniger unnötige Prüfungen), kleineres Bundle (Zone.js fällt weg), moderner Standard — die Zukunft von Angular.
Nachteil
Neuer, weniger alte Tutorials/Antworten im Netz; man muss in Signals denken.
Alternative
Der klassische Weg mit Zone.js. Funktioniert weiter, ist aber der alte Stil. Wir nehmen zoneless, weil es schneller ist und der Richtung von Angular entspricht.

Fallstrick (real, kein Bug) — Windows & Zeilenenden Der allererste prettier --check . meldete 78 Dateien mit „Code style issues“ — obwohl inhaltlich nichts falsch war. Ursache: Windows.
🔍 Warum 78 Dateien „falsch“ sind, obwohl sie es nicht sind
Die Wurzel
Git steht auf core.autocrlf=true und legt Dateien beim Checkout mit Windows-Zeilenenden (CRLF, \r\n) ab. Prettier erwartet aber LF (\n) — und meldet jede CRLF-Datei als „unformatiert“.
Der Beweis
Ein Vergleich zeigte: der Inhalt ist Zeichen für Zeichen identisch — nur die unsichtbaren Zeilenenden unterscheiden sich. Also kein Stil-Problem, ein Zeilenenden-Problem.
Verstärker
Viele der 78 waren gar nicht unser Code: NX legt für mehrere KI-Assistenten generierte Skill-Ordner an (.agents/, .cursor/, .opencode/, .gemini/, .github/skills/ …). Die will man nicht mitformatieren.
🎙️ So erklärst du's im Video

„Der Anfänger-Reflex ist jetzt: einfach prettier --write . und alles platt machen. Der Senior-Reflex ist: erst verstehen, warum. Es sind zwei Dinge — unsichtbare Windows-Zeilenenden und generierte Fremd-Dateien, die uns gar nicht gehören. Beides lösen wir an der Wurzel, nicht mit dem Vorschlaghammer.“

Die Lösung — an der Wurzel 1. Eine .gitattributes erzwingt überall LF.  2. Die generierten Ordner kommen in .prettierignore.  Danach ist prettier --check . grün — und bleibt es auch im CI (Linux) und für jeden im Team.

*.png  binary

.agents/

Generiert

Es ist fremder, gespiegelter Code. Unser Formatter soll unseren Code regeln, nicht Fremd-Dateien.
Regel
Wie dist oder coverage: Generiertes gehört in .prettierignore, nicht unter den Formatter.

2 · Was ist eine Datenbank? ~1,5 Min

🎙️ Sprechtext

„Eine Datenbank ist einfach ein Ort, an dem Daten dauerhaft und geordnet gespeichert werden. Erinnerst du dich an die Vorratskammer aus unserem Restaurant-Bild? Genau das. 📦 Begriff: Datenbank
Definition
Ein System, das Daten dauerhaft, geordnet und durchsuchbar speichert — das „Langzeitgedächtnis“ deiner App.
Vorteil
Schnelles Suchen & Sortieren, viele Zugriffe gleichzeitig, schützt vor widersprüchlichen Daten.
Nachteil
Ein eigenes System, das man verstehen und pflegen muss (übernimmt für uns später die Cloud).
Alternative

4 · Das Wort „relational“: Beziehungen ~2 Min

🎙️ Sprechtext

„Jetzt der wichtigste Teil — das Wort relational. Die Tabellen stehen nämlich nicht allein, sie sind miteinander verbunden. Ein Beispiel: Zu einem Produkt gehören mehrere Bilder. Wir speichern die Bilder aber nicht ins Produkt hinein — wir geben jedem Bild einfach die id seines Produkts mit. Das nennt man einen Fremdschlüssel: ein Verweis von einer Tabelle auf eine andere.

Bei uns gibt es vier solche Beziehungen. Merk sie dir, sie erklären fast die ganze App:“

Beziehungen im StitchLab-Datenmodell Product 1 ───────< ∞ ProductImage # ein Produkt hat viele Bilder (1:n) Category ∞ ──< ProductCategory >── ∞ Product # Produkte in mehreren Kategorien (n:m) User ∞ ──< Favorite >── ∞ Product # Favoriten (n:m) User ∞ ──< CartItem >── ∞ Product # Warenkorb, mit quantity (n:m + Nutzlast)
🎙️ Sprechtext

„Zwei Begriffe fallen dir vielleicht auf. Eine Verbindungstabelle wie ProductCategory steht in der Mitte, wenn viele zu vielen passt — ein Produkt in mehreren Kategorien, eine Kategorie mit vielen Produkten. Und CartItem ist so eine Verbindungstabelle, die zusätzlich noch etwas mitbringt: die Menge (quantity). So eine Tabelle darf also eigene Spalten haben.“

📦 Begriff: Fremdschlüssel & Beziehungstypen
Definition
Ein Fremdschlüssel ist die id eines anderen Eintrags, gespeichert als Verweis (z. B. productId in der Bild-Tabelle).
1-zu-∞
Ein Produkt → viele Bilder. (Ein Bild gehört zu genau einem Produkt.)
∞-zu-∞
Viele Produkte ↔ viele Kategorien/Nutzer. Dafür gibt es eine Verbindungstabelle (z. B. ProductCategory, Favorite, CartItem).
Vorteil
Keine Daten doppelt speichern, alles bleibt widerspruchsfrei — ändere ein Produkt an einer Stelle, überall stimmt es.

🎙️ Sprechtext

Praktisch jeder Cloud-Anbieter unterstützt sie — auch unser kostenloser bei Supabase. Für ein Projekt mit klar verknüpften Daten wie unserem ist Postgres die sichere, professionelle Wahl.“

📦 Begriff: PostgreSQL
Definition
Eine kostenlose, quelloffene relationale Datenbank — einer der ausgereiftesten & beliebtesten Standards.
Vorteil
Sehr verlässlich, mächtig, überall unterstützt, große Community, gratis.
Nachteil

🔒 Sicherheit: warum wir die Data API abschalten ~1,5 Min

🎙️ Sprechtext

„Kurz, aber wichtig: Im Security-Abschnitt beim Anlegen ist die Voreinstellung ausgerechnet die unsicherste. „Enable Data API“ baut dir automatisch eine öffentliche REST-Schnittstelle über deine Tabellen — gedacht für Leute, die supabase-js direkt im Frontend nutzen. Wir machen das bewusst nicht: Bei uns redet nur das Backend über Prisma mit der Datenbank. Also schalten wir die Data API ab — kleinere Angriffsfläche, mehr Sicherheit. Genau die Senior-Denke: keine Tür offen lassen, durch die niemand gehen soll.“

🔒 Entscheidung: Data API AUS (Zugriff nur übers Backend)
Was ist das?
Eine auto-generierte REST-API (PostgREST) direkt über deine Tabellen — für Frontend-Direktzugriff. Brauchen wir nicht.
Warum aus?
Unser NestJS-Backend ist das einzige, das die DB berührt (über Prisma, den Session-Pooler-String). Was du nicht brauchst, machst du zu.
Kein RLS nötig
„Row Level Security“ schützt die Data-API-Ebene. Ohne Data API sitzt unsere Sicherheit im Backend (Guards + Rollen) — das reicht.
Prisma & Storage?
Bleiben unberührt — die laufen über eigene Kanäle (Postgres-Verbindung bzw. Storage-API), nicht über die Data API.
Fallstrick: „rote“ Logs nach dem Abschalten — harmlos! Danach steht im Dashboard PostgREST: Disabled, und im Log tauchen rote Fehler auf („schema pg_pgrst_no_exposed_schemas does not exist“, „FATAL: terminating connection“). Das ist kein Bug, sondern der Mechanismus des Abschaltens: PostgREST wird absichtlich auf ein nicht-existentes Schema gezeigt. Postgres selbst ist gesund — siehst du an „Successfully connected to PostgreSQL“. Einfach ignorieren.

📝 Willst du die Data API doch anlassen: dann „Automatically expose new tables“ AUS und „Enable automatic RLS“ AN. Für uns ist Abschalten sauberer.

❓ Häufige Frage: „Kanada-Region — komme ich aus Berlin überhaupt dran?“ ~1,5 Min

🎙️ Sprechtext

„Kurzer Einschub, weil ich das oft gefragt werde: Ich wohne in Berlin, aber gerade habe ich als Region Canada (Central) gewählt. Komme ich da überhaupt dran? — Ja, uneingeschränkt. Die Region legt nur fest, wo die Server physisch stehen — nicht, wer von wo zugreifen darf. Eine Cloud-Datenbank hängt am Internet; mit den Zugangsdaten komme ich aus Berlin, Vancouver oder sonstwo dran. Region ist keine Zugriffssperre.“

„Was die Region wirklich beeinflusst, sind zwei Dinge: die Latenz — wie weit die Daten reisen — und die Datenresidenz, also der rechtliche Speicherort (Stichwort DSGVO / PIPEDA).“

🖥️ Latenz einblenden (grobe Roundtrip-Werte)
  • Berlin → Frankfurt (eu-central-1): ~10–20 ms
  • Berlin → Canada Central / Montreal (ca-central-1): ~90–110 ms
  • Berlin → West US (us-west-1): ~150–160 ms
🎙️ Sprechtext

„Und jetzt die eigentliche Frage: Latenz für wen? Beim Entwickeln hier in Berlin sind meine Anfragen gegen die Kanada-Datenbank rund 100 Millisekunden langsamer — spürbar, aber völlig verkraftbar; das nervt höchstens bei vielen Migrationen. In der Produktion zählt aber etwas anderes: wo mein Backend und meine Kunden sitzen — nicht mein Wohnort. Als Profi optimiert man auf die echten Nutzer: Die Dev-Latenz zahle ich einmal, die Produktions-Latenz zahlt jeder Kunde bei jedem Klick.“

„Deshalb meine Wahl: Mein Studio und mein Publikum sind in Vancouver / Kanada — also bleibt die Datenbank in Canada Central. Mein Berliner Entwickler-Alltag ist dafür etwas träger, und das ist genau der richtige Trade-off. Wäre mein Publikum in Europa, würde ich Frankfurt nehmen.“

📦 Merksatz: Region = Standort, nicht Zugriff
Zugriff
Von überall — die DB hängt am Internet, nicht an einem Land. Die Region sperrt niemanden aus.
Beeinflusst
Latenz (Entfernung Client ↔ Server) und Datenresidenz (rechtlicher Speicherort — DSGVO / PIPEDA).
Faustregel
DB nah ans Backend, Backend/Frontend nah an die Kunden — nicht nach dem Entwickler-Standort wählen.
Unsere Wahl
Kunden in Kanada → ca-central-1. Entwickeln aus Berlin bleibt problemlos möglich (nur ~100 ms mehr pro Anfrage).

📝 Optional als Schaubild: eine Weltkarte mit Pfeil Berlin → Montreal („geht problemlos“) und den drei Latenz-Werten daneben — macht den Punkt in fünf Sekunden sichtbar.

4 · Den Verbindungs-String holen (Session-Pooler!) ~2,5 Min

🎙️ Sprechtext

„Damit unser Backend mit der Datenbank reden kann, braucht es eine Verbindungs-Adresse — die DATABASE_URL. Achtung, hier gibt es einen Stolperstein, der viele Stunden kostet: Supabase bietet drei Varianten an, und wir brauchen ganz gezielt die Session-Pooler-Variante.“

🎬 Bildschirm

🖥️ Schritt für Schritt
  • Oben rechts auf Connect klicken.
  • Zum Abschnitt Connection string gehen.
  • Session pooler wählen — nicht „Direct connection“, nicht „Transaction pooler“.
  • Den String kopieren (Host endet auf pooler.supabase.com, Port 5432).
  • Im String [YOUR-PASSWORD] durch dein Database-Password aus Beat 3 ersetzen.
So sieht der String aus (Session-Pooler, Port 5432)
📋 aus dem Supabase-Dashboard kopieren — kommt gleich in die .env
postgresql://postgres.<project-ref>:<DB_PASSWORD>@aws-0-ca-central-1.pooler.supabase.com:5432/postgres
🔍 Warum ausgerechnet der Session-Pooler?
Kurz
Er ist über IPv4 erreichbar und liefert eine dauerhafte Sitzung — genau das, was das DB-Werkzeug (Prisma) für Migrationen braucht.
Direct connection
Nur über IPv6 — funktioniert später auf manchen Hostern (z. B. Render) gar nicht. Meiden.
Transaction pooler (6543)
Für Migrationen ungeeignet. Meiden.
Merke
Immer den exakten Host aus dem Dashboard nehmen (das Präfix aws-0- oder aws-1- variiert je Projekt).
Fallstrick: Sonderzeichen im Passwort Enthält dein Database-Password Sonderzeichen (@ # % / ? : & …), musst du sie im String percent-encoden (z. B. @ → %40) — sonst scheitert die Verbindung mit einem kryptischen Fehler. Einfacher: im Dashboard (Reset-Button) ein Passwort nur aus Buchstaben + Zahlen setzen — dann passt der String 1:1.

2 · Was ist Prisma (ein ORM)? ~1,5 Min

🎙️ Sprechtext

„Datenbanken sprechen eine eigene Sprache namens SQL. Man kann sie lernen — aber Prisma nimmt uns den Großteil ab. Prisma ist ein ORM, ein Übersetzer zwischen unserem TypeScript-Code und der Datenbank. Wir beschreiben unsere Tabellen einmal in einer Datei, und Prisma erledigt den Rest: Es legt die Tabellen an und gibt uns bequeme, typsichere Funktionen zum Speichern und Abfragen. Und weil es typsicher ist, warnt uns der Editor sofort, wenn wir etwas Falsches abfragen.“

📦 Begriff: ORM (Object-Relational Mapping) — Prisma
Definition
Ein Übersetzer zwischen Code-Objekten und Datenbank-Tabellen. Du schreibst normalen Code, das ORM erzeugt daraus die SQL-Befehle.
Vorteil
Kein SQL von Hand, typsicher, Autovervollständigung, ein Modell als „einzige Wahrheit“.
Nachteil
Für sehr komplexe Spezial-Abfragen stößt man irgendwann an Grenzen (dann schreibt man gezielt doch SQL).
Alternative
SQL direkt, oder andere ORMs (TypeORM, Drizzle). Wir nehmen Prisma wegen Typsicherheit & Lesbarkeit.

4 · Das Datenmodell schreiben ~3 Min

🎙️ Sprechtext

„Jetzt der Kern: Wir beschreiben unsere Tabellen in einer Datei — tief in unserer Backend-Struktur, passend zur sauberen Architektur aus Teil 1. In Prisma heißt eine Tabelle ein model, jede Zeile darin eine Spalte. Schau, wie direkt das unser Diagramm abbildet:“

schema.prisma (Auszug)
📄 libs\backend\shared\database\prisma\schema.prisma
// Prisma 7: die Verbindungs-URL steht in prisma.config.ts (Beat 5), NICHT hier.
datasource db { provider = "postgresql" }
generator client { provider = "prisma-client"  output = "../generated/prisma" }

enum Role { USER  ADMIN }                     // feste Auswahl

model Product {
  id          String  @id @default(uuid()) @db.Uuid   // PK
  slug        String  @unique                     // U (eindeutig)
  name        String                              // EN-only: EINE name-Spalte
  priceCents  Int                                 // Geld als Integer-Cent
  isShowcased Boolean @default(false)
  isPublished Boolean @default(true)
  images      ProductImage[]                      // 1:n
  categories  ProductCategory[]                   // n:m
}

model ProductImage {
  id          String  @id @default(uuid()) @db.Uuid
  productId   String  @db.Uuid                    // FK-Feld
  product     Product @relation(fields: [productId], references: [id], onDelete: Cascade)
}

model Favorite {                                  // Verbindungstabelle (n:m)
  userId    String @db.Uuid
  productId String @db.Uuid
  @@id([userId, productId])                     // zusammengesetzter Primärschlüssel
}
🔍 Die Schema-Bausteine (= dein ER-Diagramm)
model
Eine Tabelle (z. B. Product). Jede Zeile = eine Spalte.
@id / @@id
Der Primärschlüssel. @@id([a, b]) = zusammengesetzter PK (die Verbindungstabellen).
@unique
Dieses Feld darf nur einmal vorkommen (das „U“ im Diagramm).
@relation · onDelete: Cascade
Der Fremdschlüssel (FK). Cascade = löschst du ein Produkt, verschwinden auch seine Bilder/Verknüpfungen.
? · @db.Uuid
String? = darf leer sein (nullable). @db.Uuid = echter Postgres-UUID-Typ statt Text.

CI wird rot: npm ci beim ersten Push

🎬 Situation

Erster Push nach GitHub → der CI-Workflow (Actions) startet automatisch — und der Schritt Run npm ci wird sofort rot (exit code 1). Alle folgenden Schritte werden übersprungen.

🔍 Warum passiert das?
Der Fehler
npm ci installiert nur, wenn package-lock.json byte-genau zur package.json passt. Bei jeder Abweichung bricht es ab und druckt die Kommando-Hilfe (die -w/--workspace-Zeilen, die du im Log siehst).
Die Ursache
Deine package-lock.json entsteht lokal unter Windows; auf dem Linux-CI-Runner ist sie nicht „streng deckungsgleich" — und npm ci verzeiht das nicht.
Verstärker
Der CI lief zusätzlich auf Node 24, unser Projekt aber auf Node 22. Versions-Unterschiede zwischen lokal / CI / Server machen extra Ärger.
🎙️ So erklärst du's im Video

„Es gibt zwei Wege zu installieren. npm install ist nachsichtig — es aktualisiert die Sperrdatei bei Bedarf. npm ci ist streng: Es besteht auf eine perfekt passende Sperrdatei und ist für saubere CI-Server gedacht. Klingt ideal — aber wenn deine Sperrdatei unter Windows entsteht und der Server Linux ist, passt sie oft nicht exakt. Deshalb nehmen wir im CI bewusst npm install.“

Die Lösung In .github/workflows/ci.yml: npm ci → npm install und node-version 24 → 22.
.github/workflows/ci.yml
      - uses: actions/setup-node@v5
        with:
-         node-version: 24
+         node-version: 22
          cache: 'npm'

-     - run: npm ci
+     - run: npm install
Merksatz Node-Version überall gleich halten (lokal · CI · Server), und im CI npm install statt npm ci — das erspart dir genau diese roten Häkchen.

📝 Nebenwirkung: Läuft im CI danach auch e2e (Playwright), kann es weiter fehlschlagen — e2e braucht eine laufende App + Datenbank und gehört nicht ins schnelle CI-Gate. Dann e2e aus dem CI-Lauf nehmen (siehe Fallstrick 3 unten).

CI wird rot: frontend:typecheck

🎬 Situation

Nach dem npm install-Fix kommt CI weiter — und bleibt am Schritt run-many … typecheck hängen. Lokal (npx nx typecheck frontend) exakt derselbe Fehler: „Found 10 errors" — verteilt über tsconfig.app.json und tsconfig.spec.json.

📦 Erst mal: was ist typecheck?
build
„Lässt sich die App bauen?" — Angular baut mit esbuild, schaut nur auf die App-Config (tsconfig.app.json). ✅
test
„Funktionieren die Tests?" — führt den Code wirklich aus. ✅
typecheck
Ein extra strenger Kontrolleur: der pure TypeScript-Compiler geht mit tsc --build … --emitDeclarationOnly alle Typen durch — inkl. der Test-Dateien. Genau der stolpert.
🔍 Warum stolpert er? (eine Wurzel, viele Folgefehler)
Wurzel
Der typecheck-Befehl (tsc --build) will „composite"-Projekte, die Typ-Deklarationen (.d.ts) erzeugen. Angulars Config ist aber für den esbuild-Bauer getrimmt (bundler/preserve, kein composite). Die beiden beißen sich.
+ Altlast
Die Test-Config hatte zusätzlich die alte Modul-Suche moduleResolution: "node10" — die verträgt sich nicht mit customConditions (aus deinem Scope-Setup; braucht node16/nodenext/bundler).
🔥 Dominosteine
Von den 10 Fehlern waren die meisten Folgefehler: weil node10 das Modul @angular/core/testing nicht mehr findet, „verschwand" auch der Typ dahinter — und plötzlich meckerte test-setup.ts über errorOnUnknownElements. Kein eigener Bug — nur ein Domino, der mit der Wurzel mitfiel.
Wichtig
Alles von Nx generiert (Commit 01 war deshalb schon rot) — kein Fehler von dir. build & test blieben die ganze Zeit grün, die App ist gesund.
🎙️ So erklärst du's im Video

„Zehn Fehler klingt nach Chaos — ist aber fast alles ein Problem, das Dominosteine umwirft. Und der Senior-Trick: nicht raten. Erst messen (die Fehler exakt lesen), dann eine funktionierende Vorlage suchen — unser Backend macht denselben typecheck und ist grün. Also schaue ich, was das Backend anders macht, und ziehe das Frontend nach.“

🧠 Der Senior-Weg: messen → Vorlage finden → angleichen → absichern
1. Messen
npx nx typecheck frontend — die echten Fehler lesen, nicht raten.
2. Vorlage
npx nx typecheck backend ist grün. Der Unterschied: Backend-Configs sind composite und referenzieren einander. Das ist das Muster.
3. Angleichen
Frontend-Configs auf dasselbe Muster ziehen (Diffs unten).
4. Absichern
Guardrail: nach dem Fix müssen typecheck und test/build/lint alle grün sein — sonst zurück. Nie ein funktionierendes Ziel gegen ein kaputtes tauschen.
Sofortmaßnahme (erst mal grün werden) Solange der Fix nicht sicher verifiziert ist: typecheck aus dem CI-Gate nehmen. CLAUDE.md definiert das schnelle Gate ohnehin als lint · test · build. So ist CI sofort grün, ohne etwas kaputtzumachen.

CI wird rot: e2e-Timeout (Playwright)

🎬 Situation

Der Schritt e2e bricht ab: Error: Timed out waiting 60000ms from config.webServer — bei frontend-e2e:e2e und backend-e2e:e2e.

🔍 Warum?
Was ist e2e?
End-to-End: testet die ganze App wie ein echter Nutzer (ein Browser klickt sich durch) — und braucht dazu eine laufende App + Datenbank.
Das Problem
Playwright will die App starten (webServer) und aufrufen — im schnellen CI läuft aber keine App und keine DB. Nach 60 Sekunden Warten: Timeout.
Unterschied
Unit-Tests (test) prüfen einzelne Bausteine isoliert — schnell, ohne App/DB. e2e prüft das Zusammenspiel — langsam, mit App/DB.
Lösung e2e gehört nicht ins schnelle Gate (CLAUDE.md sagt das ausdrücklich). Erstmal raus — später als eigener Job mit hochgefahrener App + Supabase-Test-DB (kommt in Teil 8).

📝 Nach Commit 06 fährt unsere CI-Zeile lint test build typecheck — aber weiterhin ohne e2e (typecheck-Story: Fallstrick 2).

CI wird rot: backend-shared-database:build — der Prisma-Client fehlt

🎬 Situation

Lokal ist alles grün (nx run-many -t lint test build typecheck), aber nach dem Push wird die CI rot: @stitchlab-yvr/backend-shared-database:build schlägt fehl — und via nx-bail fallen backend:build/test/typecheck gleich mit weg.

🔍 Warum lokal grün, in CI rot?
Die Ursache
Der generierte Prisma-Client (src/generated/prisma) ist bewusst gitignored — generierter Code gehört nicht ins Repo. Lokal hast du ihn (von db:generate); die frische CI-Checkout-Kopie hat ihn nicht.
Die Folge
Der tsc-Build der Datenbank-Lib importiert ../generated/prisma/client — findet ihn nicht → rot. Der Rest kippt per nx-bail hinterher.
Merke
Generierter Code wird nicht committet, sondern in jeder Umgebung neu erzeugt — lokal, in CI, beim Deploy.
🎙️ So erklärst du's im Video

„Klassischer „works on my machine“-Fall: Der Prisma-Client wird generiert, nicht von Hand geschrieben — deshalb ignorieren wir ihn in git. Aber dann muss ihn jede Maschine selbst erzeugen. Lokal habe ich das längst gemacht, die CI startet bei null. Lösung: ein db:generate-Schritt in die CI, vor dem Build.“

Die Lösung In .github/workflows/ci.yml nach npm install einen Schritt npm run db:generate einfügen (vor nx run-many). Braucht keine DB-Verbindung — prisma generate ist offline.
.github/workflows/ci.yml
        - run: npm install
+       # Prisma-Client (gitignored) VOR build/typecheck erzeugen - offline, ohne DB
+       - run: npm run db:generate
        - run: npx nx run-many -t lint test build typecheck
Gilt auch fürs Deployment Dasselbe Muster beim Deploy (Render): der Build-Befehl muss prisma generate enthalten — z. B. npm ci && prisma generate && nx build backend && prisma migrate deploy.

Merke: Was gehört ins schnelle CI-Gate?

📦 Lokales Schnell-Gate (CLAUDE.md): nx affected -t lint test build · CI zusätzlich: typecheck
✅ lint
Code-Stil & Regeln — schnell, keine externen Abhängigkeiten.
✅ test
Unit-Tests — schnell, isoliert.
✅ build
Baut die App(s).
✅ typecheck
Config-Macken geglättet (Fallstrick 2) — läuft seit Commit 06 in der CI mit. Schnell, ohne externe Dienste.
🐢 e2e
Braucht App + DB → eigener, langsamerer Job (Teil 8), nicht ins schnelle Gate.

📝 Faustregel: Ins schnelle Gate kommt nur, was schnell und ohne externe Dienste läuft. Alles, was eine laufende App, Datenbank oder Secrets braucht, wird ein eigener Job.
